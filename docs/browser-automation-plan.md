# OA 浏览器自动化改造方案

核对日期：2026-10-15。本文按当前源码区分已实现、规划中和实网待验证的能力。Playwright 继续负责确定的页面操作；本地测试、请求样例和历史现场记录各有证据范围，不能替代当前 OA 的端到端验收。具体操作见 [执行流程](oa-flow.md)。

## 当前实现与边界

| 能力 | 已实现 | 仍未实现或待验证 |
| --- | --- | --- |
| 登录态复用 | 可选保存并加载 OA 的 Cookie、localStorage、IndexedDB；加载后重新验证门户认证 | 每次任务仍创建浏览器和 context；不恢复标签页、sessionStorage 或未保存表单，没有跨进程账号租约 |
| 批次准备 | 校验整个发票清单、业务字段和已有办理记录，再逐票创建本地草稿 | 不启动 OA，不合并多票，不提供批次内常驻浏览器；草稿写盘没有事务回滚 |
| 单票执行 | 一任务一票、一组项目/科目/付款输入；浏览器启动前验证单个 PDF，主单严格核对完整票号集合 | 不能填写已有多票合并单，也没有单据级多科目分摊模型 |
| 指定旧单打开 | `oa:open` 按已知 `bizId`、`taskId` 打开原单，核验目标地址、可见表单和唯一单号，可严格核对预期单号 | 不自动核对票据、金额、经费和流程状态，不衔接本地任务或自动续跑 |
| 执行续跑 | 按精确 BPM 域名寻找唯一未关闭标签，缺页或多页停止，不回退新建 | 仍按页面控件推断阶段，没有目标单号锁定及持久化业务检查点 |
| 查询命令 | 已实现待办、经费列表、预算科目的请求和私有响应文件保存 | 基于用户提供的请求样例；响应字段、预算 CSRF 来源及业务成功判据尚待实网校准，未接入自动选项或回执 |
| 写操作保护 | 创建、上传、付款保存、主单保存、最终确定都有单次操作边界；结果不明停止 | 进程重启后不能仅靠内存标志恢复写操作，仍需查验原单 |
| 提交核验 | 最终确定前重新核对表单及 OA 路线；配置有效回执规则后刷新已打开单据核验 | 站点示例仍有 `TODO`；提交后关页或必须重新查询的场景尚未接入，不能仅凭点击宣告成功 |
| 证据记录 | 已有阶段事件、分类错误和部分脱敏诊断；工作进程关闭全量调试产物 | 统一的脱敏截图/DOM/响应证据包、保留期限及可复现夹具生成仍在规划中 |

## 推荐的执行结构（规划）

```mermaid
flowchart LR
  Plan[单据计划：票号、科目、金额] --> Queue[同账号串行队列]
  Queue --> Runner[单据执行器]
  Runner --> Session[专用浏览器会话]
  Session --> OA[校园 OA]
  Runner --> Checkpoint[按单号保存检查点]
  OA --> Observe[页面回读与响应观察]
  Observe --> Checkpoint
  Observe --> Evidence[脱敏失败证据与本地回归夹具]
```

此图是目标结构。当前队列只保证一个本地服务实例中的任务串行，不协调另一个服务或独立 CLI；`Job` 仍只含一张发票。可选 DeepSeek 审核 JSON 也没有扩展这一业务模型：它只在用户同意后复核既定字段，保存不可变版本和摘要，执行前核对哈希，不生成页面操作代码。

### 1. 专用会话与明确的生命周期

已实现 `OA_REMEMBER_SESSION=true` 和可选 `OA_SESSION_STATE_PATH`。默认缓存位于 `<OA_DATA_DIR>/browser-session/storage-state.json`；父进程在启动 worker 前解析为绝对路径。缓存只保留允许的学校域名状态，移除过期 Cookie，目录权限为 `0700`、文件为 `0600`，通过临时文件替换保存。加载失败回到正常登录，缓存保存失败不会重放报销动作；显式账号密码模式不加载或覆盖手动登录账号的缓存。

门户认证成功时保存，正常关闭且会话仍连接时更新。`oa:connect`、`oa:open` 和三类查询命令使用独立有界面浏览器，不接管已有 CDP 标签。通用 CLI 仍可使用 CDP，现有关闭函数会调用浏览器关闭接口；共享会话的所有权和关闭策略尚未由专用管理器隔离。

下一步先建立显式任务上下文，再实现批次内常驻会话及账号租约。当前 worker 隔离了环境变量和模块全局状态，不能直接改为一个循环；应先把输入、阶段、超时、取消和回调移入任务上下文。独立管理器持有会话，任务只租用且不负责关闭共享浏览器。若引入本机专用 profile，还需目录锁，不复用个人 Chrome 主 profile。

### 2. 按单据恢复与批次模型

`batch:check` 在生成草稿前检查清单完整性、文件真实路径、PDF 解析结果、票号/哈希重复、已确认分类、报销字段及本地活跃任务。清单中已有 `liveForms`、条目 `documentNumber`、`jobId` 或非允许的待办状态时，整批停止；未知状态也停止。`batch:draft` 仅生成一票一个本地草稿，所有输入先完成验证，实际写盘仍是顺序执行。不能将旧记录删除后重新建单作为恢复方式。

已有原单时，可用 [旧单打开命令](open-reimbursement.md) 先检查页面。该命令默认使用 `isReadOnly=false`，可加 `--read-only` 请求只读页面；两种模式均无自动编辑、保存和提交。它仅在明确认证失效时尝试一次 CAS 恢复到同一目标，403、单号不符或页面不明不会触发新建。目标 ID 应取自已核实的原单链接，不能猜测未校准查询响应中的字段。

通用 `START_FROM` / `RESUME_EXISTING` 仍要求现存且唯一的 BPM 标签；它与 `oa:open` 没有自动衔接。传统 `formMode=reuse` 是检查最近单据后寻找可复用空单的流程，也不等于按指定原单恢复。已有多票单不能交给单票执行器。

规划中的检查点至少包含单据号、完整票号集合、项目编号、科目分摊、整数分金额、最近核验阶段、写入是否存在不确定结果，以及证据时间和来源。创建、上传、付款保存、主单保存和流转分别记录“已尝试”与“已核验”。恢复时重新查询原单并核对业务内容；匹配不完整则停止写入，已完成的付款或关联经核对后跳过。

### 3. 页面操作、查询与回执

三类查询入口均已实现请求层和本地模拟测试：

| 命令 | 当前用途 | 尚待校准 |
| --- | --- | --- |
| [`oa:tasks`](todo-task-api.md) | 门户页面内同源 POST 查询待办，默认第 1 页、10 条，保留 JSON 响应 | 任务字段、总数、状态和原单链接；不自动遍历分页或打开链接 |
| [`oa:funds`](funding-list-api.md) | 在已打开原单内按对话框字段 POST `easySearch.load`，解析项目表格（已实网验证） | 多页（`pageCount` > 1）时的翻页参数尚未观察到 |
| [`oa:budgets`](budget-outlays-api.md) | 在已知原单的活动页面/iframe 内，携带实时 CSRF 查询指定经费的单页预算科目（已实网验证） | 超过一页时的分页行为尚未观察到；缺失、冲突或无效 token 时请求前停止 |

查询命令只报告收到的响应，HTTP 200 不代表业务查询成功，未知结构也不当作空列表。结果存入本机数据目录的私有文件，不在终端打印正文或 Cookie。查询函数可接收已有认证的页面或上下文，但尚未接入网页经费下拉框、单据恢复或提交回执。

最终确定已有独立保护：核对同一单据及 OA 生成路线，点击尝试前设置标志；请求结束和弹窗关闭只代表传输观察完成。只有经校准的回执同时匹配单号、金额和提交状态，工作台才记为 `submitted`。没有站点配置时仍可能执行最终点击，但结果为 `submission_unknown` / `needs_review`，不能自动重试。人工核对的 `verified` 也不等于系统回执。

打开流转弹窗和最终确定使用不同规则：前者仅在完全未观察到请求、弹窗、提示、遮罩或导航且按钮仍可用时，最多尝试 3 次；后者一旦尝试就不重试。创建阶段另有一次明确登录失效的专项恢复，必须尚无单据标识、编辑页、上传或提交，不能重放不确定的创建结果。详细条件见执行流程。

下一步应从真实页面校准保存响应及回执字段，再接入按原单查询的核验路径。保留网页登录和业务操作，通过查询与页面回读提高核验确定性；尚未验证的内部写接口不直接重放。

### 4. 可复现的失败证据

规划中的常规记录包含阶段、耗时、页面/框架身份、适配器版本、控件匹配数量、错误码和业务结果是否已核验。失败时补充脱敏控件结构、局部截图及相关请求的路径、状态和允许记录的业务字段。

登录页不采集密码、验证码、Cookie、SSO ticket 或原始请求头；业务页不整页长期保存银行卡等字段。截图先遮盖敏感区域，DOM 先移除表单值和票据个人信息，再写入任务私有目录。现有全量调试开关不是已经完成的脱敏方案；完整本地 trace 需要明确的调试模式和保留期限。

实网失败应形成可脱敏复现的夹具并增加针对性回归。模拟页面通过只证明该夹具通过，不能代替真实 OA 验收。

## 后续实施与验收顺序

1. 在真实会话验证缓存复用和指定原单打开，取得三类查询的响应样本，校准预算 CSRF 来源及业务字段。
2. 建立可复用的原单业务快照与脱敏失败证据，核对单号、票号集合、金额、经费和流程状态。
3. 实现显式任务上下文、专用会话管理及跨进程账号租约，再让批次复用浏览器。
4. 将单票计划扩展为单据、票据明细和经费分摊，加入持久化检查点及不确定写入的恢复规则。
5. 用真实流程校准保存和提交回执，验证刷新、关页及重新查询场景，再扩大批量执行。

验收关注每批登录次数、阶段耗时、人工接管次数、恢复原单的结果、重复写入数和回执核验率。目前没有足够实网数据承诺速度倍数或成功率。具体个人单据的进度保留在本机办理记录，不作为通用流程或源码常量。
