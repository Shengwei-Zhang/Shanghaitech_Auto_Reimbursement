# 真实 OA 执行流程

核对日期：2026-10-15。下文描述当前代码能力，并保留注明日期的历史现场证据；历史操作记录不代表今日 OA 状态。本次仅核对源码和文档，未重新运行构建、测试或真实报销。

## 执行范围

工作台提供任务参数，Playwright 在学校 OA 页面中进行操作。工作台任务默认 `action=submit`，完成登录、新建用款申请单、经费选择、发票处理、付款配置、表单填写和保存，再点击在 2026-09-16 录制中再次确认的 `#advance` 打开“流转确认”；选择 `action=save` 时止于保存及其核验。**用户确认执行提交任务后，程序在核对无误时自动单次点击最终“确定”。审批人使用 OA 已生成的路线，不猜选或修改。**

最终确认前再次核对同一单据号、金额、发票、付款工号、附件数、用途及经费；确认唯一“流转确认”中的“/网上预约报销审批”规则，以及环节、处理人、发送消息和分组号均已填写。支持真实表格中的合并行；遇到未校准的可编辑选择、必填错误或多个确定按钮时停止。CLI 和工作台采用同样的自动确认逻辑。旧任务的人工确认记录保持兼容。

| 当前能力 | 已实现 | 边界及待验证项 |
| --- | --- | --- |
| 单票执行 | 一个任务包含一张发票及一组经费、预算、付款输入 | 不支持已有多票合并单或多科目分摊 |
| 批次准备 | `batch:check` 校验全清单，`batch:draft` 逐票生成本地草稿 | 不连接 OA、不合并单据；已有办理记录会阻止整批重新生成 |
| 登录态缓存 | 可选复用 OA Cookie、localStorage、IndexedDB，加载后重新认证核验 | 不恢复浏览器标签或未保存表单，无跨进程账号租约 |
| 旧单打开 | `oa:open` 按已知 ID 打开并核对唯一单号 | 无自动编辑和业务内容核验，未接入任务续跑 |
| 查询 | 待办、经费列表、预算科目请求及私有响应文件已实现 | 实网响应、字段映射及预算 CSRF 来源待校准，不是自动回执 |
| 提交结果 | 配置有效站点规则后，从已打开单据刷新核验单号、金额和状态 | 站点示例仍有 `TODO`；无可靠回执时为待核验，不记作提交成功 |

多票单据模型、持久化恢复检查点、共享浏览器管理和查询回执衔接仍在规划中，见 [改造方案](browser-automation-plan.md)。

## 操作、成功判据、异常处理

具体阶段契约由 `src/automation/contracts.ts` 统一定义，并通过本地会话接口提供给界面。

点击主表单“提交”后，在当前标签页的主页面与全部子框架查找“流转确认”（含 `role=dialog`），不局限于报销编辑 iframe，也不采用其他旧标签页的弹窗。发现唯一弹窗后才进入核对并自动确认；已有弹窗不再次点击主表单提交。打开弹窗最多点击 3 次：每次点击后正常观察至少 4 秒（测试短超时按比例缩短），仅在未观察到请求、弹窗、遮罩或提示，页面地址不变且原按钮可用时重试。任何请求（即使结束）、请求失败、新窗口、原生提示或跳转都阻止重试；打开弹窗的重试规则不适用于最终“确定”，最终按钮一旦尝试点击就永不自动重试。耗尽等待后保持结果未知，不推断已经最终提交。

主单保存只点击一次。点击前监听本页 XHR/fetch/document 请求，等待其结束并安静 750 毫秒，且加载遮罩消失后才准备流转。请求失败或超时停止；此等待仅避免保存/打开弹窗交叠，不代替业务成功回执。

有界面的 OA 浏览器使用实际窗口大小作为网页视口（`viewport: null`），不固定为 1440×1000；拉伸窗口时页面可重新计算表格和 iframe 高度。无头模式保留固定尺寸。连接已有 CDP 会话时保留已有上下文的视口设置；当前关闭函数仍调用浏览器关闭接口，尚无管理共享浏览器所有权的独立生命周期机制。

门户认证不使用主题颜色白名单。在学校 HTTPS 域名下识别 `/<主题>/index.html` 路径，排除登录和认证回调，要求无可见登录表单且已出现事项搜索框或“工作台＋办事大厅”导航。红、橙、蓝、绿、紫及随机选择后的主题均按页面控件判断，进入工作台及待办任务中心保留当前主题。随机按钮是否使用独立路径不作假设；测试同时覆盖五种颜色路径和额外主题路径。认证未完成时不会触发搜索和备用报销入口。

认证探测过滤隐藏重复控件，不使用第一个匹配项作为登录依据；可见密码框或登录按钮用于识别登录表单，单独的用户名元素不代表未登录。各框架和标签页并行探测，单轮每个框架最多等待 500 毫秒，同一框架不叠加未完成探测。登录按钮点击不等待整页加载；认证日志区分入口响应、填写凭据、点击返回与等待门户，等待期间每 10 秒记录未响应/读取失败的框架数量，不输出凭据或带参数网址。

| --- | --- | --- | --- |

| 流转核验 | 最终确定请求结束后按配置刷新读取单据 | 同一单据与金额进入已校准提交状态 | 无配置或缺失回执记为结果未知并保留现场 |

## 已移除的脆弱行为

- 经费单元格通过 `columnname` 定位，用 Playwright 定位器点击；不再用 iframe 内坐标点击顶层页面。
- 逐单元格输入，不依赖 Enter 自动跳到某列。
- 不直接赋值 `actualTotalAmount`、`reimbursementReimbursementAmount`、`reimbursementSettlementAmount` 等只读汇总字段。
- 支付的打开、选择、确认、保存均在明确步骤里单次执行；等待函数只观察 DOM。
- 创建用款申请单后，等待确认弹窗及编辑页期间持续检查主页面和 iframe 内可见的登录/登陆超时提示；发现失效立即报告认证错误，不自动确认超时弹窗。只有满足下述“创建入口登录超时恢复”的全部条件时，才允许一次重新认证和进入创建；其余情况停止并保留现场。通用“出现错误”及隐藏提示模板不作为会话失效证据。
- 工号及付款金额通过命名列精确比较，金额使用整数分，不用文本包含关系。
- 付款保存后只在“个人银行卡”页签的数据表核验记录，排除 Liger 的 `.l-grid1` 固定勾选列副本；真正的两条数据行仍按两条处理，不能按金额相同合并。核验通过后才填写经费金额、附件张数、用途和报销事由。经费单元格带常驻输入框时直接填写并读取输入框的值；只读汇总仍由 OA 计算。
- 经费三列优先按内部列名定位，缺少该列名时以准确的中文表头定位（报销金额/元、附件张数、用途），再通过表头列标识找到数据格，不猜列序号。无常驻输入框时按录制点击格内 `div`，等待输入框后填写，再按录制第 51 步点击 `.l-grid2 > .l-grid-body` 的空白处结束编辑，不把 `blur()` 等同于鼠标提交，也不用 Enter 推进焦点。点击位置必须命中表格空白，不能命中行、按钮或遮罩；浮动编辑框必须与目标单元格位置重叠。核验读取单元格可见文本或格内输入值，不能以浮动编辑框保留的值代替已提交数据。每列单独记录定位、输入、空白点击和回读结果；数字列失败时记录期望/实际值，用途只记录长度，不输出业务文本。
- 个人银行卡弹窗的支付金额按用户确认的方式直接填写实报金额，统一保留两位小数（如 `200.00`、`200.50`、`200.05`），替换原值后明确失焦；最多等待 5 秒让金额控件完成格式化。按整数分比较 `200`、`200.00` 或正常千分位格式，零值、空值、掩码和错误金额均不能通过；核验成功后才点击保存。日志分别记录收款人回填、金额输入与付款保存，失败提示区分回填未完成、金额未接受及实际金额不符。
- 多个项目、预算或按钮匹配时停止，不取第一个。
- 失败后进入“已暂停 · 查看异常页面”，浏览器最多保留 5 分钟；关闭、停止或超时后结束，不自动续跑。
- 除工作台导航外不做阶段级重试。失败记录包含分类和恢复建议，不包含原始密码、异常 DOM 或银行字段。

## 可选回执校准

自动填写和最终确认不依赖此配置，自动宣告提交成功需要此配置。需要系统自动核验保存/流转结果时，复制 `config/oa-site.example.json` 为自己的站点配置，替换全部 `TODO`，在 `.env` 设置 `OA_SITE_PROFILE=配置文件路径`。

需要校准：

1. 主表单保存请求的精确路径，以及响应 JSON 中真正代表业务成功的字段与值。HTTP 200 不足以证明成功。
2. 回执区域、单据号、金额及流程状态字段。单据号应是字段本身的值，不含“单据编号：”标签；读取输入框 value 或普通元素文本。
3. 明确的已保存状态、已提交状态，两组不能重叠。不能以关闭弹窗或按钮灰色作为成功判据。

先确认写入响应，再刷新读取，避免请求尚未完成就刷新。最终点击与回执校验分别记录，HTTP 成功或弹窗消失不能代替业务回执。当前适配器支持从已打开的 BPM 页面/iframe 刷新读取同一单据；若学校提交后关闭表单或需要重新查询，仍须扩展回执适配。已实现的查询命令尚未接入这一核验链路。

`verification=user_confirmed` 表示用户反馈，人工核对状态 `verified` 不等于系统提交回执。`verification=receipt` 表示系统观察结果；提交任务还须与最终确认前的单号、任务金额及已校准提交状态全部匹配，工作台才记为 `submitted`、显示“流转已核验”。无配置时仍可能执行最终点击，随后以 `submission_unknown` / `needs_review` 记录，禁止自动重试；只保存的任务也不会记为已提交。

## DeepSeek 边界

保留对用户明确提出的业务歧义提供建议的入口，例如用途与项目关系是否清晰、还缺什么依据。另有可选的报销计划审核：仅对有发票的真实草稿，在用户明确同意后发送用途、说明、金额、附件数、经费类别、项目、预算和票面金额；不发送工号、票号、PDF 或文件路径。

模型必须原样返回既定业务字段，改值或额外字段均拒绝，仅允许给出摘要及疑点。程序在本地加入付款输入、发票身份和 `fileRef: invoice.pdf`，保存不可变 `reimbursement.vN.json` 及 SHA-256 引用；启动、出队和 worker 执行前核对计划哈希，执行前另核验发票哈希。审核计划是可选功能，不替模型授权改字段、选文件、生成选择器或执行代码，也不构成多票单据模型。操作及数据范围见 [DeepSeek 审核说明](deepseek.md)。

## 登录态缓存与任务边界（2026-10-15）

设置 `OA_REMEMBER_SESSION=true` 可复用登录态，`OA_SESSION_STATE_PATH` 可指定缓存位置；默认是 `<OA_DATA_DIR>/browser-session/storage-state.json`，未设置数据目录时使用 `data`。worker 启动前解析为绝对路径，避免工作目录变更后读到不同缓存。Playwright storageState 保存允许学校域名的 Cookie、localStorage 和 IndexedDB，过滤过期 Cookie，目录权限 `0700`、文件权限 `0600`，原子替换保存。

加载后仍通过门户控件确认认证；缓存损坏或过期回到正常登录，保存失败不重试报销。显式账号密码模式不加载或覆盖手动登录账号缓存。缓存不包括 sessionStorage、打开的标签页或未保存表单，各任务仍有新浏览器和 context。`oa:connect`、`oa:open` 和查询命令使用独立有界面浏览器及手动认证模式。

本地服务队列一次运行一个任务，但独立 CLI 或其他服务实例没有共享账号锁。只有草稿可启动，服务重启将未完成执行标为中断；人工核对/释放操作不自动续跑。持久化业务检查点和跨进程会话管理尚未实现。完整环境变量说明见 [配置说明](configuration.md)。

## 指定旧单打开与执行续跑（2026-10-15）

`npm run oa:open -- --biz-id <原单ID> --task-id <原任务ID> --document-number <原单号> --read-only` 在交互终端启动独立浏览器，认证后打开固定学校 BPM 路径，核对完整目标参数、可见表单和唯一单号。`--document-number` 可选，提供后必须精确匹配；`--read-only` 请求只读页面，省略时为 `isReadOnly=false`，两种模式均无自动编辑、保存或提交。仅明确认证失败允许一次 CAS 恢复到原目标，403、目标不符和页面不明均停止。按 Enter 后关闭本次浏览器，详见 [旧单打开说明](open-reimbursement.md)。

目标 ID 来自已核实的原单链接。该入口不核对票号集合、金额、经费分摊或流程状态，也未接入本地任务恢复。`START_FROM` / `RESUME_EXISTING` 则依赖现存 BPM 标签：精确匹配域名、忽略已关闭页，多个候选报 `resume_page_ambiguous`，缺少候选报 `resume_page_missing`，不回退新建。续跑阶段仍按 UI 推断，没有持久化单据身份锁。传统 `formMode=reuse` 的空单检查流程与指定旧单打开不同；多票原单不能交给单票续跑。

## 查询命令及证据边界（2026-10-15）

CLI 与网页任务执行统一在启动浏览器前检查 `UPLOAD_FILE_PATH`：必须是存在、非空、可读取的单个 `.pdf` 文件，内容以 `%PDF-` 开头。目录、缺失文件、空文件、无读取权限或非 PDF 内容立即给出中文说明，避免已经创建 OA 单据才在上传阶段失败。此检查沿用工作台一票一任务的合同，不从目录中默认选取第一张；每张发票单独创建任务，不同经费项目或预算科目分别办理。文件头校验不代替 PDF 解析、发票号识别或 OA 验真。


## 真实查询入口与加载状态（2026-10-10）

校园门户同时提供“报销单查询”和“报销单查询（电子签章）”：前者进入 `sapbpm.shanghaitech.edu.cn/bpm`，后者进入 `sapbpm-new.shanghaitech.edu.cn:9091/bpm-new`。报销单创建（电子签章）使用后者；普通系统查询为空不能替代电子签章系统查重。现有电子签章地址保持不变。

历史现场曾通过已登录 Chrome 页面按完整票号在两个“本人”查询入口检查，未匹配票据时仍可看到未筛选的历史单据列表。本人查询不等于全校范围查重或发票可报销性证明，某时点的零条结果也不能作为后续再次新建的依据。具体票据与单据进度仅保留在本机办理记录。

实网观察到查询页先显示 0 条，再显示加载和真实记录。查询适配现在在触发查询前监听同源报销查询路径的 XHR/fetch，必须观察到请求开始、成功结束并安静后才读取表格；未发出请求、HTTP 错误、网络失败或未结束均停止，最后仍检查加载遮罩。传输完成不当作业务成功或报销回执。新增夹具覆盖延迟发请求、异步渲染及查询未发请求；请求路径筛选尚待自动化实网执行核验，不以模拟测试代替联调。既有检查至少三张单据的策略未修改。

创建页显示“用款申请单”（非特定业务）以及“采购预付及报销单”（线上采购申请或入库的设备，含低值设备、家具、耗材、工程、图书、服务）。混合票据必须先确认是否关联采购或入库，并按实际用途和预算归类；不能仅凭发票金额或目录名决定单据类型。

## 批次准备与中断恢复（2026-10-15）

批次命令和清单格式见 [批次说明](invoice-batches.md)。`npm run batch:check -- <清单.json>` 在任何草稿写入前验证整批：目录内 PDF 文件名集合、文件真实路径、已确认分类、票号/哈希重复、重新解析后的票号/金额/大小/哈希、报销字段及本地活跃任务。`npm run batch:draft -- <清单.json>` 通过相同校验后生成一票一个、默认待提交的本地草稿，不启动浏览器。整批先验证不等于写盘事务；草稿仍顺序写入，I/O 中途失败没有自动回滚。

批次检查先读取已记录的办理进度。存在 `liveForms`（兼容单票 `invoiceNumber` 与合并单 `invoiceNumbers`）、条目 `documentNumber`、`jobId` 或非待办状态时整批停止，即使本地任务库为空。未知条目状态也停止；不自动跳过部分发票，不把历史查重结果作为放行依据。没有状态的旧清单兼容原流程，显式待办状态仅接受 `not_started`、`awaiting_user_details`、`ready`。

单票自动化的关联检查只读取主单 `invoiceGrid` 可见文本，以完整 20 位号码比对，票号集合必须只有当前任务的目标号码。上传弹窗中的文件名、隐藏模板、较长数字中的票号子串均不能证明已关联；票面总额、实报金额和支付总额继续以整数分核验。历史现场证明票夹可关联多张发票，但这不代表当前单票执行器支持合并单；多票原单不能交给单票任务填写。

发现已有单据或不确定写入时，先打开原单核对票号、金额、经费、付款和流程状态，不能重新创建或上传。票夹“查验通过”、勾选完成、关联弹窗关闭和主单发票区出现，均不能替代主单逐票回读、保存或提交回执。具体单号、分类分摊及办理进度放在本机私有清单，不写入通用文档或测试；实际用途和用户确认决定分类，不能把某批科目固化成财务规则。
